UI SOURCE TRACE
---------------
frontend/src/pages/TrackBWorkspacePage.tsx
- runPlannerDecision() validates project, token, temporal result, and question.
- It calls trackBApi.decisionWorkspace(projectId, result.analysis_id, plannerQuestion, token).
- It stores the response in decision state.
- The displayed screenshot is the decision state branch, not the terrainPlanningRun branch.

frontend/src/lib/api/trackB.ts
- decisionWorkspace() uses HTTP POST.
- Endpoint: /api/v1/projects/{project_id}/track-b/analyses/{analysis_id}/decision-workspace
- Request body: {"planner_question": plannerQuestion.trim() || null}
- Response type: TrackBPlannerDecision.

backend/app/api/v1/track_b.py
- planner_decision_workspace() validates the project dataset scope and calls
  route_question(question).
- It sends terrain_measurement questions to build_track_b_terrain_planner_decision.
- It sends planning_multi_evidence or documents.search questions through
  _run_track_b_planning_question(), which creates and executes a PlanningRun.
- All other questions, including this site-context question, fall through to
  build_track_b_planner_decision().

backend/app/services/track_b_ai.py
- build_track_b_planner_decision() reads the Track B analysis manifest.
- It builds facts from temporal analysis values and manifest evidence.
- It calls the Track B AI provider and validates evidence references against the
  fixed set BEFORE_RASTER, AFTER_RASTER, SITE_GEOMETRY, TEMPORAL_ANALYSIS.
- It writes planner_decision.json under the Track B analysis artifact path and
  returns TrackBPlannerDecisionResponse.

backend/app/services/planning_orchestrator.py
- This is not on the screenshot's normal execution path.
- Its context.site_surroundings branch is only reached by execute_planning_run()
  after route_question() returns that tool.

3. ROUTER CLASSIFICATION
========================
The current backend/app/services/data_requirement_router.py was evaluated with
the exact question.

ROUTER_STATE=planned
ROUTER_CAPABILITY=site_context
ROUTER_TOOLS=["context.site_surroundings"]
ROUTER_REQUIRED_EVIDENCE=[]

Responsible branch:
- temporal = _contains_any(q, _TEMPORAL_TERMS)
- temporal is false for this question.
- site_context = _contains_any(q, _SITE_CONTEXT_TERMS)
- "berhampiran" and "kemudahan" and "pendidikan" are site-context terms.
- The site-context branch returns capability="site_context" and tools=("context.site_surroundings",).

Therefore the router itself does select site-context for this question.
The divergence occurs because planner_decision_workspace() uses route capability
only for terrain_measurement and planning_multi_evidence/documents.search. It
does not dispatch route.capability == site_context to the Planning Agent helper.
The final else branch calls build_track_b_planner_decision() instead.

TEST/UI DIFFERENCE
------------------
The normal PlanningRun tests and earlier controlled acceptance exercise the
planning_orchestrator path, where route.tools is executed. The Track B UI calls
the decision-workspace endpoint, whose non-terrain/non-document fallback uses
only the Track B temporal analysis manifest. This is the exact reason tests can
prove site-context routing while the screenshot lacks site-context evidence.

5. RASTER/TEMPORAL EVIDENCE EXPLANATION
=======================================
The Track B temporal analysis path is:
frontend TrackBWorkspacePage.analyze()
 -> trackBApi.analyze()
 -> POST /api/v1/projects/{project_id}/track-b/analyze
 -> backend analyze_temporal_pair()
 -> persisted analysis manifest.

backend/app/services/track_b.py analyze_temporal_pair() constructs manifest
 evidence containing:
- before raster dataset with role=before
- after raster dataset with role=after
- server-owned site geometry with role/site geometry metadata

The manifest also contains deterministic temporal measurements and summary
values. build_track_b_planner_decision() passes these facts to the Track B AI
provider. Its instructions and validator permit only these decision references:
BEFORE_RASTER, AFTER_RASTER, SITE_GEOMETRY, TEMPORAL_ANALYSIS.

Thus the screenshot tags are the Track B decision contract, not the normal
PlanningRun ToolEvidence contract. They prove the decision brief is based on
change-detection evidence, not that site-context evidence was queried.
